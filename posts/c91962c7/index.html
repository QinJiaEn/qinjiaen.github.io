大文件 Excel 解析内存飙升(OOM)排查与极限调优纪实

业务场景：财税系统申报表与底稿计算（跨表公式引擎）

技术栈：Java 17, Apache POI, Spring Boot, G1GC ,JVM

1. 背景与问题现象

在开发税务申报底稿计算模块时，业务需要同时将三个大型 Excel 文件（序时账、底稿、申报主表）加载到内存中，并通过 22 个 Service 进行复杂的跨表公式计算，最终将结果 write 写入磁盘生成物理文件。

  • 现象：在单线程异步执行时，通过 JVisualVM 监控发现，堆内存（Used Heap）在计算期间会一路狂飙至 1.7G - 2.0G，引发了对多并发场景下 OOM（内存溢出）的严重担忧。
  • 目标：查明内存飙升元凶，在保证业务（最终能成功导出完整 Excel）的前提下，将内存峰值压制到最低。

2. 踩坑记录与排雷（避坑指南）

在探索极限降内存的过程中，经历了以下几个极具欺骗性的方向：

❌ 坑 1：物理毁灭 DOM 节点（破坏文件结构）

  • 思路：在 for 循环中计算完一行后，直接通过 sheet.removeRow(row) 或 cellIterator.remove() 销毁单元格节点。
  • 后果：致命的业务 Bug。由于业务最后需要调用 workbook.write(os) 保存结果文件，中途销毁节点会导致最终导出的 Excel 变成只有部分数据的残缺表或空白表。在 DOM 模式（XSSFWorkbook）下，只要最后还要写盘，整个 XML 树就必须完整存活。

❌ 坑 2：盲目听信 AI 的幻觉 API 与流式读取

  • 幻觉 API：某些资料建议调用 CollaboratingWorkbooksEnvironment.clearAll()。经查证，POI 源码根本不存在此方法。
  • 张冠李戴的 SXSSF：被建议使用 SXSSF 解决大文件 OOM。事实上，SXSSF 仅适用于单向流式写入，完全不支持我们业务中极其依赖的随机读取和公式计算（Formula Evaluator）。

❌ 坑 3：JVM 乱下“紧箍咒”（IHOP 死亡循环）

  • 思路：试图通过 -XX:InitiatingHeapOccupancyPercent=20 强迫 G1GC 在 400M 时去扫地。
  • 后果：由于存活对象的体积远大于 400M，导致 JVM 陷入疯狂的 Concurrent Marking（并发标记）死循环。CPU 飙升至 100%，居委会大妈只贴标签不扔垃圾，导致程序假死。

3. 终极探秘：剥洋葱式的内存剖析

为了找到内存真相，我们剥离了所有 Spring 业务代码，写了一个纯粹的**基线测试类 (MemoryBaselineTest)**，得到了底层真相：

  1. 绝对的物理铁底（654.45 MB）： 通过强制 System.gc() 后测得，三大工作簿加载成 DOM 树后，一滴水分不掺的物理体积就是 654MB。配合 Spring 框架本身的开销，1.2G 的基础存活内存是无法逾越的物理法则。 (注：得益于前置开发的 ShadowWorkbookUtil 影子表过滤机制，否则原生几十万行的序时账足以将这 654MB 撑爆至数 GB。)
  2. 飙升的波峰（临时 XML 垃圾）： 从 1.2G 冲到 1.8G 的那 600M~800M 空间，并非内存泄漏，而是 POI 底层在执行 getCellValue 和解析公式时，瞬间产生的海量短命 XML 解析碎屑（String, Cursor 等）。

4. 破局之道：黄金杀招与最佳实践

优化一：代码级“防内存泄漏”杀招

在 22 个 Service 的循环遍历中，公式引擎（Evaluator）会缓存大量的 AST 语法树。这是唯一会演变成长期内存泄漏的元凶。 解决方案：在计算循环内部，高频调用清空缓存方法，逼迫引擎吐出中间结果。

Java

优化二：JVM G1GC 顺水推舟调优

  • 在 2G 内存受限环境的压测配置： 不瞎配置 IHOP，让 G1GC 自动发挥。1.2G 进老年代，剩下 800M 给年轻代装临时垃圾，满了自动 Minor GC 清理。 java -Xms2G -Xmx2G -XX:+UseG1GC "-Dfile.encoding=UTF-8" -jar tax-admin.jar
  • 满足目标的jvm参数: java -Xms2G -Xmx2G -XX:+UseG1GC -XX:+UnlockExperimentalVMOptions -XX:G1MaxNewSizePercent=15 -XX:MaxGCPauseMillis=50 "-Dfile.encoding=UTF-8" -jar tax-admin.jar
